# ADR 103: Review fixes of 2026-10-25 — login limits, hashing wait, push per session, Admin fields, attached registrations

Status: Accepted. Amends ADR 093 (login limits), ADR 100 (Argon2id), ADR 102 (Web Push), and
the role rule of FR-4.5 from ADR 040/084.

## Context

A security review of the changes from 2026-10-21 to 2026-10-25 found:

1. **Login limits did not hold for parallel requests.** `StartLogin` counted failed attempts,
   hashed the password, and only then stored the failure. Since ADR 100 at most two Argon2id
   hashes run at once, so parallel requests waited in a queue after passing the count check.
   A test with 20 parallel wrong passwords for one account from one address reached the
   password check 20 times instead of 5 (SC-008, SC-043).
2. **One login flood blocked every login.** The wait for a hashing slot had no limit, so a
   burst kept both slots busy and later logins, password changes, and MFA changes waited until
   the write timeout.
3. **Push subscriptions outlived the session.** Only the web client's logout removed a
   subscription. Sessions that the server ended (password change, Admin account change,
   expiry) left the device subscribed (FR-32.3).
4. **An Admin without MFA still saw Admin-only fields.** `GET /api/v1/players/{id}` showed
   other players' login names and roles to any ADMIN, also without a second factor (SC-040).
5. **Registration onto an existing player kept GUEST.** A code that attached a login to an
   existing player without one (for example a quick-add GUEST) kept that player's role, so
   the new user could not sign up for raids.

The owner decided on 2026-10-25: fix 1 to 4, and attached registrations also become MEMBER.

## Decision

A first version of this change (PR #171, commit 22a00e2) was reviewed again on 2026-10-25.
The review found that a login attempt could stay counted as a failure after correct
credentials, and that the client-side push re-binding (keyed on the player ID, with a
`localStorage` owner marker) could miss a new session, treat a missing marker as consent, and
race with logout. The owner asked for the most secure design; a third review then raised the product
question whether an opt-in belongs to a session or a device, and the owner chose the device.
This section is the result.

- **Login attempt lifecycle.** The limit check and storing the attempt as failed run in one
  transaction before the password is hashed (`auth.Repo.ReserveLoginAttempt`); with the single
  database connection (DR-9) parallel attempts are counted one by one. The stored attempt then
  ends in exactly one state at the credential decision (`auth.loginAttempt`): a wrong password,
  an unknown username, or an inactive account keeps it failed; correct credentials mark it
  successful immediately, before the hash upgrade, MFA, and session creation, so none of those
  can leave it counted as a guess; any return before the decision (no hashing slot, request
  ended, database error) deletes it. Marking and deleting use a context detached from the
  client's cancellation and bounded to 5 seconds; a failed write fails closed (the attempt
  keeps counting as failed) and is logged, which a third review on 2026-10-25 accepted as the
  right trade-off over a recovery mechanism. While an attempt is undecided it counts, so
  at most the limit's number of attempts are checked at once.
- **Bounded, cancellable wait for a hashing slot.** A request waits at most 5 seconds for one
  of the two Argon2id slots and stops waiting when its request ends; then it answers
  `503 server_busy` with `Retry-After: 5`, and its attempt is deleted. Unknown usernames get the
  same answer (SC-009). A busy hash upgrade after a verified login waits for the next login.
- **A push subscription belongs to a player on a device** (owner decision after the third
  review, 2026-10-25: keep the opt-in across sign-ins of the same player, never for another
  player). The browser gets an HttpOnly `raid_device` cookie (32 random bytes, 400 days); a
  subscription stores the SHA-256 of it (`device_hash`, migration 081 adds the column, no
  rows are lost). The rules, all enforced on the server:
  - the same player signing in again on the device keeps the subscription;
  - every session start (login, MFA, security key, registration) first deletes the
    subscriptions of other players on that device; if that fails, no session is issued;
  - logout deletes the actor's subscription on that device;
  - an own password change deletes it on the player's other devices, an Admin change of
    password, login name, or role on all devices, in the same transaction as the sessions
    (`push.RevokeForPlayer`).
  After every sign-in, keyed on a sign-in counter rather than the player ID, the browser checks
  in with `POST /api/v1/push/subscriptions/sync`: the server confirms the actor's own
  subscription (and attaches it to this device, for rows from before migration 081 or a
  cleared cookie) and deletes another player's. This covers a browser that lost its device
  cookie. The account tab shows the state the server reports, and reads it again when the tab
  becomes visible. Enabling, disabling, the check-in, and the logout clean-up run one after
  another (`runExclusive`); the permission prompt stays outside that queue so it still belongs
  to the click. The queue covers one tab; across tabs the server stays authoritative.
  A session-bound variant (subscription deleted with its session, re-enable after every
  sign-in) was built first and replaced, because it made players lose notifications at every
  session expiry, which defeats their purpose.
- **Admin fields need MFA.** Responses shared with other roles treat an ADMIN without TOTP or
  a security key like a RAIDLEADER for other players' account fields (`accountViewer`).
- **Attached registrations become MEMBER.** When a registration code attaches a login to an
  existing player without one, a GUEST becomes MEMBER; a higher role stays. Players who
  already had a login keep their role (FR-4.10).

## Consequences

- A login flood from many addresses still slows logins down, but each request now fails after
  at most 5 seconds instead of holding a connection until the write timeout.
- Notifications continue across session expiry for the same player on the same device. A
  browser that lost its device cookie relies on the client check-in after sign-in to clear a
  previous player's subscription.
- No new dependency. API changes: the new `503 server_busy` answer, the
  `raid_device` cookie, and `POST /api/v1/push/subscriptions/sync`.
